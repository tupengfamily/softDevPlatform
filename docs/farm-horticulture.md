## 二、必须说清的一个坑：产量差 1000 倍

引擎的产量公式是 `panicles × grains × weight / 1e6`，隐含了「weight 是**千粒重**」这个 1000 的除数。

园艺作物的 `weight` 是**单果重**（番茄 150g、白菜 2500g），直接套 `/1e6` 会把 5000kg/亩 算成 5kg/亩 —— 10 种作物**全部被判 L5「理论不可行」、产量 0**。

修复方式是给 `CropConfig` 增加 `weightPer` 字段（weight 对应的个数）：

```java
// 禾谷类：千粒重
double eyRaw = (panicles * grains * weight) / (1e3 * 1000);  // = /1e6
// 园艺：单果重
double eyRaw = (panicles * grains * weight) / (1e3 * 1);     // = /1e3
```

`SimEngine` 与 `FarmPlayService.yields()` 两处必须同步改 —— 展示与结算用同一条公式，这是项目一贯的"单一事实源"。

**排查线索**：如果新增作物全部是 L5 且产量趋近 0，先查这个除数，不要一个个调参数。

几个结果值得注意，都是真实农学而不是数值凑的：

- **番茄东北 L5**：露地无霜期不够，生产中必须用早熟品种或大棚。`aatReq` 已经从 2200 收到 1900（早熟），仍不够 —— 保留这个结论，它教玩家"有些地方露地种不了"；
- **草莓华南 L4**：草莓需要低温成花，华南冬季太暖，产量只有 151kg/亩；
- **郁金香华南 L5、东北 L5**：华南春天来得太快（春化不足），东北冬天低于球根耐寒极限（-18℃）；
- **菊花东北 L1 > 江南 L2**：菊花是短日植物，东北夏季日照长但秋季降温快、昼夜温差大，切花品质反而好 —— 但这条是模型副作用（没有光周期通道），已在代码注释里标注。

## 五、visual 语义：从形态族到作物 id

### 5.1 改造动机

原先 `visual` 是**形态族**（`leafy` / `vine` / `bush` / `flower`），一个族多作物共用一张 3D 贴图。好处是省素材，坏处是**后端无法区分作物形态**：适种评级的无霜期/pH、病虫害清单都只能按族给，块茎（马铃薯）和根菜（萝卜）跟叶菜共用参数。

### 5.2 新语义

`visual` 现在是**每种作物自己的标识**：

- 4 种粮食作物**保持不变**（`rice` / `wheat` / `corn` / `soybean`）—— 前端已有对应贴图，且存量数据库 `t_farm_season.visual` 里就是这 4 个值，改了会造成大面积贴图失效；
- 18 种园艺作物的 visual 改为**各自 crop id**（如 `cabbage` / `grape` / `rose`）。

### 5.3 存量数据兼容：不写迁移脚本

存量 `t_farm_season.visual` 里仍有 `leafy` / `vine` / `bush` / `flower` 等旧值。**不写 DB 迁移脚本** —— 迁移脚本要么改数据（风险高、要备份），要么加映射表（还得维护同步）。改动的做法是加一层**解析层** `engine/CropVisual.java`：

```java
// 同一个入口，同时认「新的作物 id」与「存量的旧族名」
Form form = CropVisual.formOf(visual);
```

`CropVisual` 内部维护一张 22 作物 id + 4 旧族名 + 4 粮食旧值的映射表，把它们统一归到 7 个形态族（GRAIN / LEAFY / VINE / BUSH / FLOWER / TUBER / TREE）。所有**依赖形态族参数**的地方（无霜期、pH、病虫清单）都改走这个入口，而不是直接 `switch(visual)`。

### 5.4 直接 switch 的陷阱

如果不做这层改造，`SuitabilityEngine.minFrostFree("cabbage")` 会落到 default 分支，拿到的不是白菜的无霜期 85 天而是通用值 —— 评级会**无声变差**（玩家只看到分数下降，不知道为什么）。同理 `PestEngine.forCrop("grape")` 若只认旧族名，会让所有园艺作物拿到 RICE 的病虫清单，病虫压力直接归零。

**因此**：任何需要按形态取参数的地方，一律先 `CropVisual.formOf(visual)`，禁止直接 switch 这个字段。`CropConfig.visual` 的字段注释里已写明这条约束。

### 5.5 前端过渡期

前端 `scene/config.js` 建立三层结构：`CROP_TEXTURE`（作物专属贴图，暂无）→ `CROP_FAMILY`（作物 id → 族）→ `FALLBACK_FAMILY`（族名回退）。未来补齐专属贴图时，只需在 `CROP_TEXTURE` 加一行即可自动切换，无需改渲染逻辑。

## 六、已知局限

1. **没有设施栽培**：番茄/黄瓜/草莓在北方冬季会被判冻死，这是露地口径的正确结果。大棚需要单独一套环境模型（温湿度、补光、CO₂），不在本期；
2. **多年生果树只做了简化**：葡萄与梨按「秋播→越冬春化→春梢→挂果」的一年生口径跑，共享冬小麦的春化机制，但没有「定植多年、花芽分化、大小年」的多年生模型 —— 现实中葡萄是 3–5 年挂果、梨是 4–6 年，本作里第一年就能收，属于简化；草莓按一年生栽培处理，同理；
3. 花卉按 kg 当量结算（菊花 40g/支、郁金香 25g/支），没有"支"这个单位；
4. 菊花的光周期机制缺失，用积温+播期近似，花期误差 1–2 周；
5. 园艺作物价格波动远大于粮食，当前是固定产地中位价，没有季节波动与订单溢价（S14 市场系统的范围）。
