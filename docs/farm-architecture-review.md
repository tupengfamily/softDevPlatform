# 农场游戏：架构评估与引擎选型建议

> 评估时间：2026-10-20 · 对应代码：`spring-boot-learning/.../farm/`（26 文件 5837 行）+ `frontend-learning/src/{views,components}/farm`（4513 行）

---

## 一、现状画像

| 层 | 技术 | 规模 | 职责 |
|---|---|---|---|
| 表现层 | Vue 3 + Element Plus + Three.js 0.160 | 4513 行 | 田地渲染、面板、抽屉 |
| 领域服务 | Spring Boot + JPA | `FarmPlayService` **1531 行** | 取数、折算、装配 FarmView |
| 模拟引擎 | 纯 Java，无状态静态方法 | 3108 行 | 逐日推进的农学模型 |
| 持久化 | SQLite | `t_farm_plot` / `t_farm_action` / `t_farm_weather` | 只存「种子 + 玩家动作」，不存推演结果 |

**游戏循环**（关键）：**请求驱动，没有 tick**

```
玩家操作 → POST /api/games/farm/{action|input|harvest|advance}
        → FarmPlayService.replay()：从播种日逐日重算到今天
        → SimEngine / PestEngine / SoilEngine / DisasterEngine 全部消费同一条 DVS 轨迹
        → 装配 FarmView → 前端渲染
```

没有任何「服务器每秒 tick」或「WebSocket 推送」，状态演进是**离散日**。

---

## 二、这套架构和你这个游戏类型匹配吗

**匹配，而且匹配得比"上引擎"更好。**

你的游戏本质是「日推进 + 重模拟 + 轻操作」的农业经营，它的技术特征：

| 特征 | 需要的架构能力 | 当前是否满足 |
|---|---|---|
| 状态按「天」演进 | 离散事件推进，无需实时循环 | ✅ |
| 玩家决策稀疏（一天几次） | 请求-响应足够，长连接是浪费 | ✅ |
| 数值必须可解释、可复现 | 确定性模拟（种子 RNG）、回放 | ✅ 引擎是纯函数 |
| 防作弊 / 排行榜 | 权威模拟必须在服务端 | ✅ |
| 农学模型复杂（春化、氮素、病害三角、十年回放评级） | 适合强类型语言 + 单元测试 | ✅ Java 比 GDScript/Lua 更稳 |
| 要和学习平台共用账号/成就 | 同栈零摩擦 | ✅ JWT/RBAC 直接复用 |

**结论：这是「仿真内核类」游戏，不是「实时 3D 动作类」游戏。前者 90% 的复杂度在规则，10% 在画面；后者相反。你目前把复杂度放对了地方。**

一个反例说明：`SuitabilityEngine` 要做「十年天气回放 + 七因子归因」，这种算力密集、强确定性、需要被测试覆盖的逻辑，放在 Unity 的 C# 里做 Web 版只会更痛苦（WebGL 下无多线程、调试困难、包体大）。

## 三、真正的瓶颈（与引擎无关）

按优先级排序：

### 1. 每次操作全量重放 —— 实测后判定：**不需要快照表**

`FarmPlayService.replay()` 从 `sowDate` 逐日算到 `today`，上限 430 天，每次 `view()` / `applyInput()` / `harvest()` 都重跑一遍。

**先测再改**（2026-10-20 实测，单用户 150 天水稻季）：

| 接口 | 耗时 |
|---|---|
| `GET /state`（含 1 次全量 replay + 4 个引擎 + JSON） | 6–10 ms |
| `GET /actions` | 2–3 ms |
| `GET /suitability`（十年天气回放、七因子归因） | 2 ms（已有 `suitCache`） |

即：**引擎本身 < 1ms，耗时主要在 HTTP + JSON 序列化**。所以「加 `t_farm_snapshot` 每 10 天落一份」在当前规模下是**过度设计**——多一张表的迁移、失效、一致性成本，换不来可感知的收益。

**已实施**：内存级记忆化（`FarmPlayService.simCache` + `simEpoch`）
- key = `userId | plotId | sowDate | today | epoch`，命中直接返回上次的 `SimResult`
- 失效：8 个写路径（advance / harvest / restart / applyMock / resetMocks / performAction / applyInput / createField）入口调用 `invalidateSim(userId)`
- 进程重启后 epoch 与 cache 同时归零，天然一致

**何时才该上快照表**（触发条件，任一成立）：
1. 单用户地块数 > 4，且前端一屏同时展示多块地
2. 接入真实气象格点 API，`weather.range()` 变成网络调用
3. 开始做「历史赛季排行」需要回放多季

届时按 `(plotId, date)` 落快照、`replay` 从最近快照续算即可；`SimEngine.simulate` 目前是纯累加器（所有累积量从 0 起），续算需要给它加一个初始状态参数——这是那时才付的成本。

### 2. 表现层没有资产管线 —— **已重构**

**改造前**：`FarmScene3D.vue` 1374 行单文件，同时负责纹理加载、天空合成、地形、作物实例、树木、野草、天气粒子、相机交互、四季切换、资源释放。且资产用 `Promise.all` 加载——**一张 404 就整页掉到 SVG 兜底**。

**改造后**（`src/components/farm/scene/`）：

| 模块 | 职责 | 行数 |
|---|---|---|
| `config.js` | SEASON / STAGE_PLAN / 密度 / 尺寸，纯数据 | ~160 |
| `util.js` | 确定性随机、平滑阶跃、软阴影、垄沟、十字面片、fBm | ~230 |
| `sky.js` | 逐像素大气天空 + 分形远山（三层） | ~250 |
| `assets.js` | 串行加载 + 真实进度 + 单张失败降级为纯色占位 + 重试 | ~130 |
| `crops.js` | 丛坐标、6 阶段 InstancedMesh、实例色、接触阴影 | ~190 |
| `FarmScene3D.vue` | 只做编排：相机、交互、天气粒子、生命周期 | ~700 |

资产管线的三条改进：
1. **进度可见**：`loadAll(specs, onProgress)` 串行推进，加载遮罩显示「正在生成实景农田 / 翻耕田面 · 62%」
2. **失败局部化**：坏一张图只让那一块退化成纯色（按资源名猜底色），不再整场白屏
3. **失败可观测**：`emit('ready', { failed })` 把降级清单抛给上层，同时 `console.warn`

**未做**：远景预渲染成单图。当前远景只有 3 个 draw call（三层山）+ 1 个天空球，收益低于维护成本；等加「村庄/仓库/多场景」时再做。

### 3. 表现与领域状态强耦合在 props

组件靠 `stage / crop / water / weather` 推演画面，没有独立的表现状态机。所以「收割」「施肥」「打药」这类一次性动作**无法播动画**——因为 props 只描述"当前是什么样"，不描述"刚发生了什么"。

**建议**：加一个轻量事件通道（`plot.events` 里塞 `{type:'harvest', at:date}`），渲染层消费后播放一次性动效。这是"手感"的来源，比换引擎便宜得多。

### 4. 演示模式 hack 与生产逻辑混在一起

`/advance`、`/weather/mock`、`/weather/reset`、`/field` 的演示偏移都写在生产 Controller 里。上线前必须抽成 `@Profile("demo")`。

### 5. 精灵切图的表现力上限

作物是「照片切图十字面片」，好处是照片级真实，代价是：
- 无法做骨骼动画（风吹麦浪只能靠整体位移/顶点着色器）
- 每株形态相同，靠镜像/旋转/缩放掩盖（相机拉到很近时会看出重复）

## 四、如果要换引擎，选哪个

先明确一件事：**换引擎解决的是"表现层产能"，不是"模拟层问题"。**

| 引擎 | Web 包体 | 适合你的点 | 不适合的点 | 判断 |
|---|---|---|---|---|
| **Three.js**（现状） | ~600KB | 已有照片级田地，零迁移成本，与 Vue 同栈 | 手写成本高，无编辑器/动画系统 | **当前最优** |
| **Babylon.js** | ~1.2MB | 自带 Inspector / 动画组 / 粒子 / GUI / 物理；`ThinInstances` 表现力强；Vue 集成简单 | 生态比 three 小，学习成本中等 | **想做动画时的首选** |
| **PlayCanvas** | ~800KB | 浏览器内可视化编辑器，美术迭代最快 | 编辑器绑定平台，代码导出后维护割裂 | 美术主导时选 |
| **Cocos Creator** | ~1.5MB | 一键导微信小游戏（农场类最实际的分发渠道）；2D/3D 都行 | 3D 品质上限低于 three/Babylon | **要上小游戏才选** |
| **Godot 4** | ~10-15MB | 开源、编辑器完善、GDScript 迭代快 | Web 包体大、加载慢、与 Spring 后端集成要自写桥接 | 桌面版才考虑 |
| **Unity** | 15-30MB | 生态最全、资产商店 | WebGL 首包过重、移动端 WebGL 掉帧、与现有栈割裂 | 不推荐 Web |
| **Unreal** | 不可用 | — | 基本不能 Web | 不考虑 |

### 明确的判断

**现在不需要换。** 三个判据，任一成立才值得迁移：

1. 需要在田里跑**运动物体**（收割机、无人机、牲畜）→ Babylon.js
2. 需要**上微信小游戏**做分发 → Cocos Creator
3. 需要**多场景切换**（村庄/仓库/加工厂）且美术工作量翻倍 → PlayCanvas 或 Babylon

如果这三条都不成立，迁移只会让你的 1374 行变成 3000 行，且丢掉现在"照片级真实"的成果。

## 五、建议路线

**短期（1–2 周，纯收益）**
1. 快照表 + 增量续算
2. `FarmScene3D` 拆分 + 资产加载进度
3. 远景预渲染成单图
4. 演示模式隔离到 `@Profile("demo")`

**中期（若要做"农事手感"）**
5. 加 `plot.events` 一次性动效通道
6. 作物加顶点着色器风场（`onBeforeCompile` 注入 sin 波），成本最低的"活起来"
7. 若 5/6 还不够 → 迁 Babylon.js，用 `ThinInstances` + `AnimationGroup`

**长期（若要分发）**
8. Cocos Creator 重写表现层，`FarmView` 当纯数据源（这一步的前提是第 1 条已经做完，因为小游戏对请求延迟更敏感）

---

## 六、一句话结论

架构选型是对的——**服务端权威模拟 + 纯函数引擎 + 离散日推进**，这是「农业仿真经营」这类游戏最省事、最可维护的形态，也是换任何引擎都替代不了的部分。

「更先进的引擎」不是当前瓶颈。真正的短板是**没有模拟快照**（性能会随地块/赛季线性恶化）和**没有表现层资产管线**（加内容成本高）。先把这两件事做掉，再谈引擎迁移。
